# Retryable invoice PDF generation

## Responsibility

Claim and render invoice-PDF jobs, retain generated bytes as evidence, and expose
status/refresh. This worker processes invoice PDFs only; sharing `local_jobs` with
other domains does not make it their general job scheduler.

## Boundary

An atomic update claims queued work. Rendering runs off the async executor, uses
the immutable issue-time snapshot, stores the document, and links it to the
invoice. Current profile changes must not rewrite issued identity/tax wording;
`invoice-lifecycle` owns historical snapshot recovery and its evidence requirement.

There are at most three attempts. A retryable failure is deferred for the rest of
the current processing pass, not retried by a timer. Open, issue/credit, PDF status,
and refresh paths trigger processing; there is no standalone queue daemon.
Refresh deduplication is transactional. Querying PDF status can therefore perform
work, not merely inspect state.

Observed recovery limitation (acceptance unconfirmed): opening a workspace resets
all running PDF jobs to queued without an age/lease test, so “stale recovery” does
not establish safe multi-instance worker fencing. Backup lease semantics must not
be inferred for this queue.
